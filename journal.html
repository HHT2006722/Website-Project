把六张画换成六张照片

2026年10月19日 · 做站记录 · 内容与定位

这个站原来叫「练习本」，放的是六张插画。问题是：那六张不是我画的，其中一张右下角还带着原作者的署名。这一条过不了「自己的内容」——就算标成「临摹」，画面里的处理我也解释不了。

所以做了一次彻底的替换：把自己拍的六张动物照片放上来，站点从「插画练习」改成「观察本」。不是换个标题就完事，而是每一处都对到新主题——首页的自述、六个标题和说明、两篇画面拆解换成拍摄笔记、关于页的器材清单，连 favicon 和分享卡片都换成了照片。

六张照片都拍于 2024年4月5日，用 iPhone 13 Pro。那天光线很杂：室内顶光、玻璃反光，还有几处射灯直接打在动物背上。

代价是画面本身不够完美：隔着玻璃、顶光、动物不配合。所以文案里不写「拍得多好」，只写这次放弃了什么、为什么放弃。这样老师问细节时，我答的是真实发生过的事。

验证：320 / 375 / 768 / 1440 四个宽度都没有横向溢出和坏图；手机端只下载 480 档，单张 15–52 KB。

隔着玻璃拍：反光、水珠和擦不掉的指纹

2026年10月19日 · 拍摄笔记 · 玻璃与反光

《玻璃后面》那张水獭，画面里同时有三层东西：水獭、亚克力管上的水珠、还有玻璃反射的室内灯。这三层叠在同一张照片上，拍完才发现最抢眼的是水珠，不是水獭的眼睛。

后来总结出三条能落地的做法。第一，把镜头尽量贴近玻璃。 贴得越近，玻璃上的指纹和划痕越虚，越容易被忽略；离得远反而全都清清楚楚。第二，用深色衣服或手挡在镜头侧面。 玻璃上的反光大多来自镜头后方或侧方的光源，挡住那一侧，画面就干净一半。第三，绝不开闪光灯。 光会直接反射回镜头，得到一片白斑，而且会惊到动物。

《鳞》那张鬣蜥能成立，是因为它离玻璃够近，而且玻璃底边那条金属框正好压在画面下缘——我把它留在构图里，当作「这是隔着看的」的证据，而不是想办法裁掉它。

拍这类照片的心理准备：十张里能用的可能只有一张，因为反光什么时候落在不碍事的位置，基本靠运气。多拍、回看、删掉，比现场纠结有用。

暗光展区：不开闪光灯怎么把主体拍清楚

2026年10月19日 · 拍摄笔记 · 曝光

展区的灯几乎都是顶光或者射灯，光从上面下来，动物一抬头，眼睛就掉进阴影里。《并排》那两头小猪之所以能拍清楚，是因为它们正好趴在墙洞里，身体朝向光线，鼻子冲着外面。

手机在这种环境下能做的其实不多，但有三件很关键。点屏幕对焦到眼睛，然后向下拖动曝光补偿（就是那个小太阳），先把它压暗一点——宁可欠曝，也不要糊。暗了还能拉回来，糊了没救。不要用数码变焦，那是裁切放大，等于把噪点一起放大；能走近就走近，走不近就接受拍不到。连拍几张再挑，动物一动，快门稍慢就虚，十张里总有一张是实的。

还有一个容易忽略的点：展区灯光偏暖甚至偏绿，自动白平衡有时会把毛色拍脏。《找吃的》那只刺猬的毛本来是浅米色，我拍的第一组发黄，重拍时对着旁边的白墙重新取样，颜色才回来。

照片只有 300 KB，为什么还要做三档

2026年10月19日 · 做站记录 · 图片与性能

六张原图都是 1920×1080 或 1440×810，单张一百到三百多 KB，看起来「不大」。但页面上的缩略图只有三百多像素宽——为了看一个小方块，下载的却是一整张原图，六张加起来 1.6 MB，手机流量和首屏时间都被它拖住。

做法是给每张导出 480、960、1600 三个宽度的 WebP（竖图是 480、960、1280），在 <img> 上用 srcset 列出候选，用 sizes 说明「这个位置在手机上接近满宽、在大屏大约 300 像素」，剩下的交给浏览器挑。实测手机端只下 480 档，单张 15–50 KB。

另外两件小事影响很大：每个 <img> 写上真实的 width 和 height，图片加载前浏览器就知道要占多高，页面不会跳；缩略图加 loading="lazy"，首屏之外的图滚到附近才下载。

踩过的坑：sizes 写错不会报错，只会悄悄挑错图。我一开始写成 100vw，桌面端就去下了 1600 宽那档，白白多花流量。判断办法是打开开发者工具的 Network 面板，改窗口宽度，看实际请求的是哪一档。

键盘也能用的灯箱

2026年10月19日 · 做站记录 · 可访问性

照片页的放大预览一开始是拿 div 加半透明遮罩自己写的：点图弹出来，点遮罩关掉。问题是键盘根本打不开。后来把触发元素换成真正的链接，并且用原生 <dialog> 加 showModal()：浏览器会自动把焦点锁在对话框里、按 Esc 关闭、把背后内容设为不可交互。

但原生 <dialog> 只解决了一半。剩下两件事要自己补：打开时把焦点放到「关闭」按钮上，关闭后把焦点还给刚才看的那张照片。否则用 Tab 键浏览的人关掉大图之后，焦点会掉回页面开头，得重新走一遍导航。

还加了一个前后切换的按钮组。手机上没有方向键，只能关掉再点下一张，体验是断的。加了之后，关闭时焦点会回到「当前正在看的那张」，而不是最初点开的那张。

测试时发现一个意外：这个浏览器里，Tab 会从「下一张」跑到背景的「跳到主要内容」，再跳回来。原生对话框理论上应该锁住焦点，实际没有锁严，所以补了十几行焦点陷阱，首尾相连。

表单的校验该由谁做

2026年10月19日 · 做站记录 · JavaScript

联系页的表单最初只做了一件事：检查输入框里有没有 @。写 a@b、test@、@x.com 测试，全部被当成有效邮箱放行，还弹出了「留言已记录」。这说明「有 @」和「是邮箱」差得很远。

现在分三层：<input type="email"> 交给浏览器做基础判断；提交时再用一条正则检查结构；每一项的错误信息通过 aria-describedby 关联到输入框，同时把 aria-invalid 设为 true，读屏软件才会念出来。另外修了一个状态 bug：上一次提交成功的提示，在后来校验失败时没有消失。

最后是一个诚实性的问题。这是纯静态站，没有服务器，表单没法真的把消息存下来。与其假装「已收到」，不如老实告诉访客：点击发送会调用系统邮件客户端，并在页面上写清「如果没弹出，请直接发邮件到某个地址」。

从一列到三列：网格的自适应

2026年10月19日 · 做站记录 · CSS 布局

照片列表一开始是按固定列数写的，手机上会挤成一条缝，或者横向溢出、需要左右拖动。后来改成 grid-template-columns: repeat(auto-fill, minmax(220px, 1fr))：容器放得下几列就排几列，每格最小 220px。手机一列，平板两列，桌面三列，不用写任何媒体查询。

导航是反过来的思路：手机上默认收起，用按钮展开；700px 以上把按钮隐藏、列表横排。这样小屏的交互状态和大屏的静态布局各自独立，不会互相打架。

验证方法不是「拖窗口看看」，而是在开发者工具里固定 320、375、768、1440 四个宽度，每次检查页面底部有没有横向滚动条。有滚动条就说明某个元素比视口宽，逐层排查。
